\section{Executable pebble game}
\label{sec:executable}

The formal pebble game on a graph $G$ (\cref{def:runPebbleGame-verdict})
cannot be computed, since it uses mathlib's lists of finite sets
(\cref{fmlnote:pebble-game-computable-core}). In this section we define
the computable pebble game on $G$, which uses lists sorted by a linear
order on $V$ instead. With it we define procedures that decide, for
$\ell < 2k$, whether a finite graph is $(k, \ell)$-sparse or
$(k, \ell)$-tight, and whether it is Laman. These procedures can be run
in Lean, and a command-line program uses the computable pebble game to
decide whether a graph read from a file is Laman.

In \cref{sec:executable-list-views} we define the sorted lists, and in
\cref{sec:executable-wrapper} the computable pebble game. It needs no
new correctness argument: its verdict accepts $G$ if and only if $G$ is
$(k, \ell)$-sparse (\cref{thm:runPebbleGameExec-isAccept-iff}). We define
the three decision procedures in \cref{sec:executable-decidable}, and
describe three ways to run them in \cref{sec:executable-backends}. We
list the examples on which they are run in
\cref{sec:executable-examples}, and describe the command-line program in
\cref{sec:executable-cli}. As for the formal pebble game, we prove no
bound on the running time of the computable one (\cref{sec:pebble-game}).

\subsection{Sorted lists}
\label{sec:executable-list-views}

The formal pebble game uses mathlib's lists in two places. The pebble
search follows the arcs of $D$ along the lists $N^+_D(a)$ of
out-neighbours (\cref{def:tryReachPebble}), and the pebble game on $G$
runs on a list of the edges of $G$ (\cref{def:runPebbleGame}). We
replace both with lists sorted by a linear order on $V$.

\begin{definition}[Sorted out-neighbour list]
  \label{def:outListSorted}
  \lean{CombinatorialRigidity.PebbleGame.PartialOrientation.outListSorted}
  \leanok
  \uses{def:partial-orientation}
  Let $V$ be a finite set with a linear order, and let $D$ be a partial
  orientation on $V$ (\cref{def:partial-orientation}). For $v \in V$,
  the \emph{sorted out-neighbour list} of $v$ in $D$ is the list of the
  out-neighbours of $v$ in $D$, the vertices $u$ with $(v, u) \in D$, in
  increasing order.
\end{definition}

\begin{lemma}[Membership in the sorted out-neighbour list]
  \label{lem:mem-outListSorted}
  \lean{CombinatorialRigidity.PebbleGame.PartialOrientation.mem_outListSorted}
  \leanok
  \uses{def:outListSorted}
  Let $V$ and $D$ be as in \cref{def:outListSorted}, and let
  $u, v \in V$. Then $u$ is an entry of the sorted out-neighbour list of
  $v$ in $D$ if and only if $(v, u) \in D$.
\end{lemma}
\begin{proof}
  \leanok
  Sorting a finite set lists each of its elements, and nothing else.
\end{proof}

So the sorted out-neighbour lists are lists $N^+_D(a)$ as in
\cref{sec:pebble-game-algorithm}.

\begin{definition}[Sorted edge list]
  \label{def:edgeListSorted}
  \lean{SimpleGraph.edgeListSorted}
  \leanok
  Let $V$ be a set with a linear order, and let $G$ be a finite simple
  graph on $V$. The \emph{sorted edge list} of $G$ is the list of the
  pairs $(\min e, \max e)$, for the edges $e$ of $G$, in lexicographic
  order. Here $\min e$ and $\max e$ are the smaller and the larger end
  of $e$.
\end{definition}

\begin{lemma}[Membership in the sorted edge list]
  \label{lem:mem-edgeListSorted}
  \lean{SimpleGraph.mem_edgeListSorted}
  \leanok
  \uses{def:edgeListSorted}
  Let $V$ and $G$ be as in \cref{def:edgeListSorted}, and let
  $u, v \in V$. Then $(u, v)$ is an entry of the sorted edge list of $G$
  if and only if $u \le v$ and $uv \in E(G)$.
\end{lemma}
\begin{proof}
  \leanok
  Sorting a finite set lists each of its elements, and nothing else. So
  the entries are the pairs $(\min e, \max e)$ for $e \in E(G)$. Such a
  pair $(u, v)$ has $u \le v$ and $e = uv$. Conversely, if $u \le v$ and
  $uv \in E(G)$, then $(u, v) = (\min uv, \max uv)$.
\end{proof}

\subsection{The computable pebble game}
\label{sec:executable-wrapper}

With the sorted lists, the pebble game on a list
(\cref{def:runPebbleGame}) gives a pebble game on $G$ that can be
computed.

\begin{definition}[The computable pebble game]
  \label{def:runPebbleGameExec}
  \lean{CombinatorialRigidity.PebbleGame.PartialOrientation.runPebbleGameExec}
  \leanok
  \uses{def:runPebbleGame, def:outListSorted, def:edgeListSorted,
    def:pebbleGameResult, thm:pebble-game-correct,
    lem:workhorseWitness-certifies, lem:mem-edgeListSorted,
    lem:mem-outListSorted}
  Let $V$ be a finite set with a linear order, let $G$ be a simple graph
  on $V$, and let $k$ and $\ell$ be non-negative integers with
  $\ell < 2k$. The \emph{computable pebble game on $G$} runs the pebble
  game on the sorted edge list of $G$ (\cref{def:edgeListSorted}) from
  the empty orientation, with the sorted out-neighbour lists
  (\cref{def:outListSorted}) as the lists $N^+_D(a)$. It returns the
  verdict on $G$ (\cref{def:pebbleGameResult}) that is an acceptance,
  given by $D$, if the game returns a partial orientation $D$, and a
  rejection, given by $V'$, if the game returns a failure witness whose
  set is $V'$.
\end{definition}

\begin{fmlnote}
  \label{fmlnote:executable-computable-core}
  The computable pebble game is formalized as the forms of the pebble
  game that take the lists as an argument
  (\cref{fmlnote:pebble-game-computable-core}), applied to the sorted
  lists. Sorting a finite set by a linear order needs no choice, so the
  sorted lists, and with them the game, can be computed. Only a
  definition that can be computed can be run by \texttt{\#eval} or
  \texttt{native\_decide}. A verdict consists of a partial orientation
  or a set of vertices together with proofs, and proofs are erased in
  compiled code. So the compiled program computes only the pebble game.
\end{fmlnote}

The verdict is well defined, as for the formal pebble game (the
paragraph after \cref{def:runPebbleGame-verdict}). The sorted edge list
lists the pairs $(u, v)$ with $u < v$ and $uv \in E(G)$, in increasing
order (\cref{lem:mem-edgeListSorted}). So it lists each edge of $G$
once, and \cref{thm:pebble-game-correct} applies to it. By its
part~(1), a returned $D$ has $\underline{D} = E(G)$, and $D$ is
$(k, \ell)$-reachable, as is every orientation that the game reaches.
By its part~(2), whose proof uses \cref{lem:workhorseWitness-certifies}
and $\ell < 2k$, a returned $V'$ is a blocking witness for $G$.

\begin{theorem}[Correctness of the computable pebble game]
  \label{thm:runPebbleGameExec-isAccept-iff}
  \lean{CombinatorialRigidity.PebbleGame.PartialOrientation.runPebbleGameExec_isAccept_iff}
  \leanok
  \uses{def:runPebbleGameExec}
  Let $V$ be a finite set with a linear order, let $G$ be a simple graph
  on $V$, and let $k$ and $\ell$ be non-negative integers with
  $\ell < 2k$. Then $G$ is $(k, \ell)$-sparse if and only if the verdict
  that the computable pebble game on $G$ returns accepts $G$.
\end{theorem}
\begin{proof}
  \leanok
  \uses{thm:pebble-game-correct, lem:mem-edgeListSorted,
    lem:mem-outListSorted, def:reachClosureComputable,
    lem:mem-reachClosureComputable}
  The computable pebble game returns an acceptance when the pebble game
  on the sorted edge list returns a partial orientation, and a
  rejection when it returns a failure witness
  (\cref{def:runPebbleGameExec}). So its verdict accepts $G$ if and only
  if this game returns a partial orientation. The entries of the sorted
  out-neighbour list of a vertex are its out-neighbours
  (\cref{lem:mem-outListSorted}). The sorted edge list lists each edge
  of $G$ once (\cref{lem:mem-edgeListSorted}). So
  \cref{thm:pebble-game-correct} applies, and the game returns a partial
  orientation if and only if $G$ is $(k, \ell)$-sparse.
\end{proof}

\subsection{Deciding sparsity, tightness and the Laman property}
\label{sec:executable-decidable}

A \emph{decision procedure} for a proposition $P$ returns either a
proof of $P$ or a proof of its negation. In Lean it is an instance of
\texttt{Decidable}~$P$, and a command or a tactic that decides $P$ uses
the one registered for $P$ (\cref{sec:executable-backends}). We
register decision procedures for three properties of a finite graph
with a linear order on its vertices. The one for $(k, \ell)$-sparsity
runs the computable pebble game. Those for $(k, \ell)$-tightness and
the Laman property add a count of the edges.

\begin{definition}[Deciding sparsity]
  \label{def:isSparse-decidable}
  \lean{SimpleGraph.instDecidableIsSparse}
  \leanok
  \uses{def:runPebbleGameExec, def:isSparse,
    thm:runPebbleGameExec-isAccept-iff}
  Let $V$ be a finite set with a linear order, let $G$ be a simple graph
  on $V$, and let $k$ and $\ell$ be non-negative integers with
  $\ell < 2k$. The decision procedure for the $(k, \ell)$-sparsity of
  $G$ runs the computable pebble game on $G$
  (\cref{def:runPebbleGameExec}). If the verdict accepts $G$, it returns
  a proof that $G$ is $(k, \ell)$-sparse, and otherwise a proof that $G$
  is not, both by \cref{thm:runPebbleGameExec-isAccept-iff}.
\end{definition}

\begin{fmlnote}
  The procedure takes the hypothesis $\ell < 2k$ as a registered fact,
  so that a command or a tactic finds the procedure without being given
  a proof. The fact $3 < 2 \cdot 2$ is registered, so at
  $(k, \ell) = (2, 3)$ the procedures of this subsection apply with no
  hypothesis given.
\end{fmlnote}

\begin{remark}[One decision procedure for each property]
  \label{rem:decidable-runtime}
  As $V$ is finite, whether $G$ is $(k, \ell)$-sparse can also be
  decided by checking the inequality of \cref{def:isSparse} for each of
  the $2^{|V|}$ subsets of $V$. A procedure of this kind decides the same
  proposition, but on a sparse graph it checks all $2^{|V|}$ subsets. We
  register only the procedure of \cref{def:isSparse-decidable} for
  sparsity, and build the procedures for tightness and the Laman
  property on it. So a command or a tactic that decides one of these
  properties runs the pebble game.
\end{remark}

\begin{definition}[Deciding tightness]
  \label{def:isTight-decidable}
  \lean{SimpleGraph.instDecidableIsTight}
  \leanok
  \uses{def:isSparse-decidable, def:isTight}
  Let $V$, $G$, $k$ and $\ell$ be as in \cref{def:isSparse-decidable}.
  The decision procedure for the $(k, \ell)$-tightness of $G$ decides
  whether $G$ is $(k, \ell)$-sparse by \cref{def:isSparse-decidable},
  and whether $|E(G)| + \ell = k|V|$ by computing both sides. It returns
  a proof that $G$ is $(k, \ell)$-tight if both hold, and otherwise a
  proof that $G$ is not (\cref{def:isTight}).
\end{definition}

\begin{definition}[Deciding the Laman property]
  \label{def:isLaman-decidable}
  \lean{SimpleGraph.instDecidableIsLaman}
  \leanok
  \uses{def:isTight-decidable, def:isLaman}
  Let $V$ be a finite set with a linear order, and let $G$ be a simple
  graph on $V$. The decision procedure for the Laman property of $G$ is
  the decision procedure for the $(2, 3)$-tightness of $G$
  (\cref{def:isTight-decidable}), since $3 < 2 \cdot 2$ and a graph is
  Laman if and only if it is $(2, 3)$-tight (\cref{def:isLaman}).
\end{definition}

\subsection{Runtime and backends}
\label{sec:executable-backends}

A decision procedure registered for a proposition $P$, such as
``$G$ is Laman'' for a given graph $G$, can be run in three ways.
\begin{itemize}
  \item The command \texttt{\#eval decide}~$P$ runs the procedure in
    Lean's interpreter, and prints its answer, \texttt{true} or
    \texttt{false}. The examples of \cref{sec:executable-examples} are
    run in this way.
  \item The command-line program \texttt{lake exe pebble-game} of
    \cref{sec:executable-cli} runs the computable pebble game, compiled
    to native code.
  \item The tactic \texttt{native\_decide} proves $P$ by running the
    compiled procedure. The proof rests on an axiom, added for it, that
    states the program's answer. So it trusts Lean's compiler, and
    mathlib does not accept such proofs. The tactic \texttt{decide}
    would instead prove $P$ by evaluating the procedure by reduction,
    trusting only Lean's type checker. It does not evaluate these
    procedures. The processing of an edge (\cref{def:tryAddEdge}) and the
    search of \cref{def:reachable-finding} are defined by well-founded
    recursion, which \texttt{decide} does not unfold.
\end{itemize}

\subsection{Worked examples}
\label{sec:executable-examples}

We run the decision procedures with \texttt{\#eval} on four graphs,
each on the vertices $\{0, \ldots, n - 1\}$ for some $n$. The file that
does so, \texttt{PebbleGame/Examples.lean} in the Lean library, records
the expected answer beside each evaluation, and the procedures return
it.
\begin{enumerate}
  \item The graph on $\{0, 1, 2, 3\}$ obtained from $K_4$ by deleting
    the edge $23$ has $4$ vertices and $5 = 2 \cdot 4 - 3$ edges, and it
    is Laman (\cref{thm:top-fin-four-minus-edge-isLaman}). The procedure
    for the Laman property answers \texttt{true}.
  \item The Moser spindle on $\{0, \ldots, 6\}$ consists of the
    triangles $012$ and $034$, a vertex $5$ adjacent to $1$ and $2$, a
    vertex $6$ adjacent to $3$ and $4$, and the edge $56$. It has $7$
    vertices and $11 = 2 \cdot 7 - 3$ edges, and the procedure for the
    Laman property answers \texttt{true}.
  \item The complete graph $K_4$ on $\{0, 1, 2, 3\}$ has $6$ edges, more
    than $2 \cdot 4 - 3 = 5$, so it is not $(2, 3)$-sparse. The
    procedures for sparsity and for the Laman property answer
    \texttt{false}. So the computable pebble game rejects $K_4$
    (\cref{thm:runPebbleGameExec-isAccept-iff}), and its blocking witness
    is $\{0, 1, 2, 3\}$. Indeed a blocking witness has at least two
    vertices (\cref{def:blockingWitness}), and a set $X$ of two or three
    vertices spans $2|X| - 3$ edges of $K_4$.
  \item The path on $\{0, \ldots, 4\}$ with the edges $01$, $12$, $23$
    and $34$ is $(2, 3)$-sparse, since a set of $s \ge 2$ of its
    vertices spans at most $s - 1 \le 2s - 3$ edges. It
    has $4$ edges, fewer than $2 \cdot 5 - 3 = 7$, so it is not
    $(2, 3)$-tight and not Laman. The procedure for sparsity answers
    \texttt{true}, and those for tightness and the Laman property answer
    \texttt{false}.
\end{enumerate}

\subsection{CLI binary}
\label{sec:executable-cli}

The command \texttt{lake exe pebble-game}~\emph{file} runs a program that
reads a graph from a file and decides whether it is Laman. The first
line of the file is $n$~$m$, the numbers of vertices and of edges. Each
of the next $m$ lines is $u$~$v$, for an edge between the vertices $u$
and $v$, where $0 \le u, v < n$. Numbers on a line are separated by
spaces, and blank lines and lines that start with \texttt{\#} are
skipped. If the file does not have this form, the program prints an
error message.

The program takes for $G$ the simple graph on $\{0, \ldots, n - 1\}$
whose edges are the pairs read, leaving out a pair with $u = v$. It runs
the computable pebble game on $G$ with $(k, \ell) = (2, 3)$, and prints
the following.
\begin{itemize}
  \item If the verdict is an acceptance, given by $D$: the line
    \texttt{LAMAN} if $|E(G)| + 3 = 2n$, and \texttt{SPARSE\_NOT\_TIGHT}
    otherwise; then a line \texttt{ARCS}~$u$~$v$ for each arc $(u, v)$
    of $D$, in lexicographic order.
  \item If the verdict is a rejection, given by $V'$: the line
    \texttt{NOT\_SPARSE}, then the line \texttt{BLOCKING}~$|V'|$, then a
    line \texttt{VERTEX}~$w$ for each $w \in V'$, in increasing order.
\end{itemize}
By \cref{thm:runPebbleGameExec-isAccept-iff} and \cref{def:isLaman}, the
first line is \texttt{LAMAN} if $G$ is Laman, \texttt{SPARSE\_NOT\_TIGHT}
if $G$ is $(2, 3)$-sparse but not Laman, and \texttt{NOT\_SPARSE} if $G$
is not $(2, 3)$-sparse. The reading of the file and the printing are not
verified. The directory \texttt{examples/} holds the four graphs of
\cref{sec:executable-examples} as input files, each with its expected
output in a comment at the top.
